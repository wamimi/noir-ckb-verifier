# SP1 verifier rejection experiment

Status: harness build and all six cases passed on 27 September 2026.
Exact errors, cycle counts, and artifact hashes are retained in
[the Week 13 evidence record](../../evidence/week-13.md).

These files extend the pinned upstream benchmark in a separate ignored checkout.
The original benchmark remains the reference for its measured binary size and
cycle count. The experimental executable includes case selection, mutation, and
assertion code, so its size and cycles are recorded separately.

## Cases

| Case | Change | Required verifier result |
| --- | --- | --- |
| `valid` | None | `Ok(())` |
| `wrong-program` | Last program-hash nibble changes from 0 to 1 | `PairingCheckFailed` |
| `wrong-public-values` | Public bytes change from empty to `[1]` | `PairingCheckFailed` |
| `changed-proof` | Zero proof bytes 484 through 515, following upstream's suggested mutation | `PairingCheckFailed` |
| `truncated-proof` | Keep only the first 99 bytes | `GeneralError(InvalidData)` |
| `wrong-verifier-key` | Flip one bit of the wrapper verifier key | `PlonkVkeyHashMismatch` |

All six required outcomes were observed in the retained run. Unexpected structured
errors are logged and fail the assertion. A panic, timeout, cycle exhaustion,
or debugger error also fails the harness. Each case runs in its own VM invocation.
The verifier may attempt both SHA-256 and Blake3 public-value hashes on failure;
negative-case cost can therefore differ substantially from the positive case.

A harness guest exit code of zero means the expectation matched. For a negative
case it means the verifier rejected the input, not that a transaction accepted
the invalid proof. The structured verifier error is retained in the log.

The wrong-wrapper-key case tests the proof/key fingerprint check. It does not
exercise an alternative well-formed verifier key with a matching fingerprint.
The truncated case tests the top-level length check, not every internal decoder
boundary. This small matrix is not a security audit.

## Reproduction

From the repository root, after the upstream positive baseline has passed:

```bash
bash scripts/week13-sp1-matrix.sh build
```

Review the build output, then run:

```bash
bash scripts/week13-sp1-matrix.sh run
```

The script retains the upstream Cargo.lock and builds with Rust 1.94.0 and
Homebrew LLVM 19. Logs and the experimental checkout live under `target/week-13`.
These verifier tests do not inspect Cell data or establish transition binding.
